# ADR-REFACTOR-06 · 货架机理：只接「取」这一半，且靠显式 `rack_type` 开启

- 状态：已采纳（R2，2026-11-13）
- 相关：G1；`scripts/rack_access.py`；`spec_layout.py`；D4
- 前置：ADR-REFACTOR-01（按存取机理分型）

## 背景

R2 要把"货架生产方式"接进引擎。但引擎的取货逻辑只有一句
`_pick_loc = rng.choice(SHELF 池)`，而上架侧根本没有"深位"概念（收货直接把数量加到
某个库位）。要完整建模，得同时改：

- 取货：从哪个深位取（前位挡后位 / LIFO / FIFO）；
- 上架：放到哪个深位（驶入式放最深、压入式放最浅、重力式放最里）；
- 移动式：开合通道要时间；
- 穿梭式：换巷道要时间。

这四件事的成本差别很大，收益也不同。一次性全做，等于把 R2 变成一个小 R3。

## 决策

1. **机理本身做成纯函数**（`rack_access.py`）：给定货道占用，算出可取的深位、
   被挡的深位、是否需要重排、物理出库顺序（FIFO/LIFO）。无随机流、无时钟，
   可以逐条手算验证。
2. **只接"取"这一半**：`_pick_loc` 选中的库位若属于多深位货道，按机理落到
   可作业的深位；被挡时发 `SLOT_BLOCKED` + `RESHUFFLE` 并计数。
   **上架仍按原逻辑**——因为改上架要动收货结算与库存写入，那会连带改
   批次、FEFO、快照三条线，属于 R5 之后的事。
3. **靠显式 `rack_type` 开启**：`spec_layout` 只在货架组声明 `rack_type` 时
   才展开深位与 `cell_id`。默认布局没有这个键 → `data/layout.json` 与历史
   逐字节一致，`rack_cells` 为空，`_pick_loc` 走原分支（D4）。
4. **物理 LIFO + FEFO 要计数，不要禁止**：驶入/压入/单端穿梭只允许后进先出，
   而批次层默认 FEFO——两者不可能同时满足。真实仓库靠重排或改货位妥协，
   游戏里应该让玩家看见代价（`FIFO_LIFO_CONFLICT` 事件 + 计数），
   而不是假装没冲突、也不是直接禁止这种组合。
5. **`effective_slots` 与 `capacity_model` 各存一份**：解析层一份、引擎一份，
   两边必须能独立算出同一个数；合并成一份就没法交叉验证"仪表盘说 100、
   仿真跑 80"到底是谁错。

## 本轮不做（明确边界）

- **上架深位选择**：驶入式"放最深"、压入式"放最浅"目前只在纯函数与门里可验证，
  没进收货结算。
- **移动式开合时间 / 穿梭车换巷道时间**：同样只在解析层与门里，没进 tick 服务时间。
  一旦进 tick，服务时长变化会改事件流——那要配合 v4 重冻，且必须与"换货架类型"
  这件事分开归因。
- **有效货位的运行时扣减**（冻结通道、维修停用）：`effective_slots` 已可算，
  但引擎的 `_pick_loc` 还没按它过滤。

## 后果

- 正向：换货架类型第一次真的改变**取货行为**（后位被挡会重排），且默认字节不变，
  所以不需要在这一步重冻——重冻留给"新关卡真的启用深位"的那一次。
- 负向：只接一半意味着"上架策略"仍是隐式的；如果玩家以为选了驶入式就完全按
  驶入式作业，会与实现有落差。这条必须写进关卡的说明，不能靠玩家猜。
- 风险：`cell_id` 是新键，若将来有人把 `spec_layout` 改成"总是展开"，
  默认布局会立刻多出库位、`pick_loc` 分布改变、v3 金标准破。护栏是
  `check_rack_access.py` 的"默认布局零货道"判据。

## 拒绝过的方案

- **一次性把上架/开合/换巷全接进 tick**：会同时改服务时长、库存写入、批次账，
  归因彻底混在一起。
- **用 `model` 字段（rack_double）判断机理**：那是 3D 资产名，已经在
  ADR-REFACTOR-01 里否掉了。
