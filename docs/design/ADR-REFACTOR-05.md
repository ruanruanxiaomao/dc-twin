# ADR-REFACTOR-05 · 新机制一律 config-gated 默认关闭 + 分代重冻 + 快照升版

- 状态：已采纳（R0，2026-11-13）
- 相关：§10；D2 / D4 / D5；`docs/design/REFACTOR_PROTOCOL.md`

## 背景

这个项目最强的东西是**字节级金标准**：8 场景 × 3 份产物逐字节一致，只归一化
`run_id` 与 `wall_clock_s`。已经做过两代重冻（v1 step 化、v2 库存、v3 批次效期），
每次都靠"旧基准永不覆盖 + 新基准按构造必红"来证明改动可归因。

这一次重构（R0–R8）比前两次大得多：货架、设备、库容、库存策略、关卡、前端、3D，
任何一项接进引擎都会改事件流。如果每接一项就重冻一次，基准会变成一张谁都不看的
快照；如果为了"保持字节不变"而不接，功能永远落不了地。

## 决策

1. **每个新机制默认关闭**，关闭时既有产物**逐字节不变**。
   关闭不是注释掉的代码，而是配置开关（缺文件 / `enabled=false` → 引擎退回旧行为）。
   判据是"I can prove it": 关闭态必须与上一代基准一致，这门比"功能能跑"更硬。
2. **一次行为变更 = 一次重冻 + 逐事件归因**。`report_refreeze.py --base vN --target vN+1`
   输出：哪份产物变了、哪个 KPI 变了多少、每种新事件出现多少次、A1–A40 是否仍全过。
3. **旧基准永久保留**：v1/v2/v3 之后还会有 v4、v5。`--check=vN` 必须永远可用。
   `REFREEZE_OK` 要求"比新基准一致"**且**"比旧基准必须不同"——
   旧基准若意外变绿，说明新机制根本没进事件流。
4. **SNAPSHOT 升版接受旧档失效**（D2）：当前 3.0，R2/R3 会到 4.0（加 `equipment_type` /
   槽位状态 / 策略计数器）。旧档**显式拒绝**，不写迁移脚本——迁移写错会静默漂移，
   而游戏存档的寿命只有一局。
5. **先立门、再动代码**：每个阶段的第一件事是把该阶段的门写出来并确认它**能失败**
   （构造反例），然后才改实现。门不能失败的阶段，不许进入下一阶段。

## 后果

- 正向：任何一轮都可以"只回退一项开关"来定位回归，而不是靠读 diff 猜。
- 负向：配置面变大（4 份新 spec + 开关），需要 `check_capacity_spec.py` 这类
  "口径自洽"门来防"配置之间互相矛盾"。这类门只能守住已知的不变量，
  新加字段时要同步加断言，否则会出现"通过了但没测到"。
- 风险：R2/R3 若同时改货架与设备并一次性重冻，归因会混在一起。
  缓解：R2、R3 各自独立重冻（v4 货架、v5 设备），不允许合并成一次。

## 拒绝过的方案

- **不重冻，改比 KPI 容差**：让漂移"合法化"，等于放弃这个项目唯一真正硬的纪律。
- **只保留最新基准**：省空间，但抹掉"这次改了什么"的唯一证据。
- **给旧档写迁移**：迁移成本高且极易静默错位（P6a 已经踩过"补空账"的坑）。
