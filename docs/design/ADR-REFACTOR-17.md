# ADR-REFACTOR-17 · 宽度轴：和深度轴同一套算术，但少一条上限、多一条障碍

- 状态：已实施（R8.10）
- 日期：2026-11-13
- 关联：ADR-REFACTOR-15（深度轴求解器）、`scripts/layout_solver.py`、
  `scripts/check_area_param.py`（`AREA_BAYS_OK`）

## 背景

R8.8 之后"面积 → 库容"在**深度轴**上闭环了：改 `size.depth`，功能带贴新后墙，货架行数
按剩余进深重排，0 冲突、可交付。但**宽度轴是假的**——`spec["warehouses"][*].racks[*].bays`
还是写死的整数，把厂房从 100 m 拉到 120 m，壳子和导航格变大了，货架一跨都不加。

这不是"没做"，是"看起来做了"：`AREA_PARAM_OK` 只验网格随尺寸变，从来不验 bays。

## 决策一：复用深度轴的形状，不新增算法范式

`free_bays_for_group` 与 `free_depth_for_group` 是同一个东西换了个轴：

| | 深度轴 | 宽度轴 |
|---|---|---|
| 主上限 | 功能带前沿 − 余量 | 东墙 − 余量 |
| 次上限 | 同 x 列里更靠后的货架组 | 同 z 走廊里更靠右的货架组 |
| 第三上限 | —（后巷已折进余量） | **待命位** − 余量 |
| 余量 | `max(1.0, ap_offset)` + 一行深 + AP | `1.0`（见决策二） |
| 放不下 | `SolveError` | `SolveError` |

宽度方向**没有"功能带前沿"这一项**：功能带是横跨整个 x 的一条 z 带，它约束进深，不约束
宽度。把它算进来是给宽度轴凭空加一条假约束——和"让行数服从 zone 颜色框"是同一类错误。

## 决策二：宽度方向不需要"后巷"余量

深度轴必须留 `rack_depth + ap_offset` 的后巷，因为每排货架**后侧也有访问点**，最后一排
贴死上限时那个 AP 就落在通道外（实测 3 条 SHELF L6 就是这么来的）。

宽度方向不同：AP 落在行的**前后**（z 方向），不落在 bay 的左右侧。最右一跨靠墙 1 m，
取货点仍然站得下人。所以余量就是 `CLEARANCE_M`。写成 `rack_length + ap_offset` 会把
20 m 宽度里的 4.5 m 白扔掉，而且没人看得出为什么。

## 决策三：待命位锚东墙，且必须"按基线重算"

第一版只算了东墙和兄弟组两个上限，宽度 +20 当场炸出 **6 条 `HOME-W-R07..R12 AP not
walkable`**：默认布局有 6 个待命位在 x=98.25（贴东墙留 1.75 m），厂房变宽后货架排到
116.6，把发车点整个吃掉。

修法与 `shift_band` 同一条纪律——**锚定关系决定谁动**：月台锚南墙、功能带锚后墙、
待命位锚东墙。所以宽度变了先让东侧那排跟着走（`x = x0 + (新宽 − 基线宽)`），
再把待命位当成货架的第三上限（`blockers`）。

幂等靠**基线绝对参照**，这里踩了一个不显眼的坑：第一版写的是
`if dx != 0: pts[i] = pts[i] + dx`，于是"100 → 120 → 100"时第二步 dx=0，点留在 118.25
——**复位静默失败，而且门看不出来**（因为货架上限被挡住的待命位也算"守法"）。
现在无条件 `x = x0 + dx` 重算，改回去就真的回得去（有单测钉住）。

没有 `area_baseline.width` 就**不平移**，与 `shift_band` 一致：猜一个常量等于给四个仓
同时改布局。这时货架会被 `blockers` 挡在待命位之前——最坏结果是少了宽度红利，
不是发车点被吃掉。

## 决策四（门）：必须做"同宽对照"，否则门只认开关

打开求解器后，**左列组也会从声明的 10 跨填到 13 跨**——那是"填满已有空隙"，
与宽度无关（宽 100 时就该填）。只看宽 120 的结果，会把这份填满当成"宽度红利"，
门就成了睁眼瞎。

所以 `AREA_BAYS_OK` 跑两次：同一份 spec、同样打开求解、一次宽 100、一次宽 120，
只认**增量**：

- 被 `east_wall` / `spawn_XX` 挡住的是东列 → 增量必须 > 0；
- 被 `sibling_zone_X` 挡住的是左列 → 增量必须**等于 0**；
- 待命位最大 x 必须跟着东墙走；
- 两次都必须 0 issue、exit 0。

右列/左列不按 zone 名硬编码，按 `blocked_by` 判——布局改名时门不会跟着瞎。

自检 2 条反例：`bays_not_solved`（拿没求解的布局当结果）、`bays_no_width_gain`
（两次都是 100，右列没涨）。后者是关键：它证明门比的是增量，不是开关状态。

## 实测（W 仓 100 → 120，深度不变）

| 项 | 100 (窄) | 120 (宽) | 差 |
|---|---|---|---|
| A / C 跨数（左列） | 13 / 13 | 13 / 13 | 0 |
| B / D 跨数（东列） | 11 / 11 | 17 / 17 | **+6** |
| 待命位东侧 x | 98.25 | 118.25 | +20 |
| 四仓货架 | 196 | 276 | +80 |
| 四仓库位 | 441 | 601 | +160 |
| issues | 0 | 0 | — |

## 未做（诚实记账）

- **充电位不在 x 约束里**：默认布局的充电位在 z 带内（x=30..42.5），货架进不了那条带，
  天然不撞。若将来有人把充电位声明到货架走廊里，`blockers` 需要把它也传进来。
- **`obstacles` 不在 x 约束里**：默认布局没有 x 方向的障碍物；同一笔账。
- **`orientation='z'` 直接抛错**，不猜方向（bay 沿 z 推时宽度轴与深度轴重叠）。
- **宽度缩小的独立负门没做**：缩到装不下仍由 `AREA_SHRINK_NEG`（L2/L3/L6 拒绝）覆盖，
  但"只缩宽度、刚好卡掉一跨"这条边界没有专门用例。
- **默认不启用**：`options.reflow_bays` 缺省关，`width_budget` 缺省无，所以
  `data/layout.json` 仍逐字节不变（sha `9dcaf196`）。
