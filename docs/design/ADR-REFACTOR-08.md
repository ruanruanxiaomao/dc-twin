# ADR-REFACTOR-08 · R4 解析库容接主链，以及 AST「密度中性」的如实记录

- 状态：已实施（R4）
- 方案依据：§11 R4 / §12.2 交叉验证 / 签核 D3（15% 容差）
- 相关：ADR-REFACTOR-03（解析层不替代 DES）、ADR-REFACTOR-06（R2 半接）、ADR-REFACTOR-07（R3 AST 耦合）

## 背景

R0 落了公式与配置，R1–R3 落了单元、货架、设备，但解析层**从来没有真正跑过数据**：

```python
for zone in wh.get("zones", []):
    for rack in zone.get("racks", []):     # 真实布局里 zones 只有多边形
```

真实布局把货架挂在 `warehouse.racks` 上，于是巷道数 = **0**，总能力 = 0，
`aisles` 为空，`warnings` 也不报——报表"干净"，因为什么都没算。

同时 `devices: []` 是写死的：即使巷道算出来了，能力也永远是 0、负荷永远 0、
瓶颈永不出现。

## 决策一 · 巷道与设备都从真实数据来

- `aisles_from_layout()`：同仓同区同 z 的货架序列 = 一条巷道；长度为行首尾端点间距；
  货位 = 架数 × 层数 × 2（每架两面）。
- `assign_devices()`：车队按**货位份额**摊到各巷道。
  不能"每条巷道都放整套车队"——那会把总能力按巷道数放大一遍，负荷率永远小于 1，
  瓶颈永远不出现，等于把解析层变成一句安慰话。

## 决策二 · 与仿真比的是「一单周期」，不是「吞吐」

解析算一单周期，仿真也量一单周期（`TASK_ASSIGNED` → `TASK_COMPLETED`）。
两边必须按**同一作业策略**：

```
一单 = 空驶取货 + 载货送达 + 空驶回位（3 段）
      + 取/放各一次站台作业（2 × station_s）
      + 取/放各一次停靠（2 × dwell_s）
```

这两个参数写在 `capacity_spec.handling` / `capacity_spec.travel_policy` 里，带
`level: assumption` 与来源，**不留在代码里调常数**。

**为什么不比吞吐**：基线场景是需求受限（45 单/h 远低于 523 单/h 的能力），
峰值场景是拥堵/截止期受限（实测吞吐反而从 56 掉到 29 单/h）。拿吞吐去比能力，
结论只会是"需求不够"或"堵死了"，与公式对不对无关。**比吞吐是假验证。**

## 实测结果（可复跑：`python scripts/check_capacity_cross.py`）

| 量 | 数值 |
|---|---|
| 巷道 | 22 条（W 16 / F1 2 / F2 2 / F3 2） |
| 名义货位 | 1496 |
| 解析一单周期 | 129.4 s |
| 仿真一单周期 | 148.7 s（38 单的均值） |
| 解析能力 | 523.2 单/h |
| 仿真能力 | 508.4 单/h（3600/148.7 × 21 台） |
| **偏差** | **2.9%**（容差 15%） |

残差 19.3 s 来自排队/等待——解析层没有排队论，这个方向（解析偏乐观）是结构性的，
不是参数错误。峰值场景的能力单独记录，**不作判据**，因为它是范式差不是公式错。

## 决策三 · AST「密度中性」必须如实记录（本阶段不改）

R3 的 AST 耦合只改巷道宽 → 节距，**不改行数**：`rows` 是布局里写死的整数。
于是 `off_locations == on_locations == 392`，巷道变窄并不带来更多货位。

这与方案书 `AST_COUPLING_OK` 写的"同地块库容密度变"、以及 `equipment_spec` 里
"省 1m ≈ 多一排货架"**是相反的**。收检方指出后，我确认属实，并做了两件事：

1. 把门的注释与测试名写清楚：`test_ast_expansion_changes_pitch_not_location_count`
   ——**故意**密度中性，而不是"忘了做"。
2. 不在 R4 里顺手改掉：改行数会改库位数 → 改拣选分布 → **金标准必破**，
   必须独立重冻，并过 `REFLOW_BOUNDARY_NEG`（L2/L23/L7/L8 越界报错不静默）。
   它是独立里程碑（R5），不是 R4 的附带项。

**后果（必须写在状态表的边界里）**：当前买窄巷道车只买到"通道更窄、导航更省"，
**买不到库容**。设备层最核心的那笔权衡尚未兑现。

## 决策四 · 解析层仍不进 tick

`capacity_model` 是纯函数：无 rng、无时钟、不写文件。R4 只把它接进**报告与门**，
不接进 tick 循环——接进去会改服务时长分布，那是另一次重冻的事。

## 实施中抓到的三个错

1. **遍历错层级**：`zones[].racks` vs `warehouse.racks` → 0 条巷道。
2. **小数被截断**：`aisle_capacity` 里 `int(d["count"])` 把 0.75 台截成 0 台，
   主仓 W 能力报 0，而总能力仍然是正的（F 仓 1.5 → 1 台）。只看总数永远发现不了。
3. **一单少算两段行程和一次作业**：最初周期 84.4 s vs 仿真 148.7 s（快 43%），
   会被误读成"解析模型乐观"，实际是少算了空驶回位与放货作业。

## 后果

- 解析库容第一次有真实数字，并进 `dc run --scope refactor`（第 5 步）与
  `out/capacity_report.json`。
- `CROSS_VALIDATE_OK` 可证伪：把周期改成 1/3，偏差 200% 当场判红。
- AST 的密度缺口被写进 ADR、状态表边界与门的命名里，不再有"看起来做完了"的空间。
