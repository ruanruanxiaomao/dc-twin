# ADR-REFACTOR-03 · 解析库容层的位置：不替代仿真，只做交叉验证

- 状态：已采纳（R0，2026-11-13）
- 相关：G4；`scripts/capacity_model.py`；`config/capacity_spec.json`；D3

## 背景

项目已经有一台**离散事件孪生**（`sim_engine.py`：泊松到达、在线派单、9 态 FSM、
电量/充电、故障重派、工位与月台排队）。资料给的是另一套东西：**静态解析公式**
（货格几何 → 单元 → 巷道聚合 → 设备时间 → 能力/负荷/瓶颈）。

两套东西都能回答"这个仓库能干多少"，但都不是对方的替代品：

- 解析层给的是**理论上限**，不考虑排队与交通拥堵，一分钟出结果，适合做规划与告警；
- 仿真给的是**实际跑出来多少**，含排队/死锁/充电，跑一小时才出结果。

## 决策

1. `capacity_model.py` 是**纯函数库**：输入 layout + rack/equipment/capacity spec，
   输出每巷道与全局的货位/有效货位/能力/负荷/瓶颈/告警。**无随机流、无时钟、不写文件**
   （R0）。R4 才接主链并产出 `out/capacity_report.json`。
2. **不进 tick 循环**。它的三个消费方是：关卡判定输入、前端仪表盘、规划关校验器。
3. **交叉验证**（CROSS_VALIDATE_OK）：
   `|throughput_sim − Q_stable| / Q_stable ≤ 15%`（D3）。
   `Q_stable = Q_m · availability_factor`（§5.4：峰值 ≠ 稳定系统输出）。
   超差**不许放宽容差蒙过去**，要能定位到"设备时间模型口径错了"还是
   "仿真有解析层没建模的交通瓶颈"。
4. 解析层与仿真**共用同一套 B1/B2/B3 修正口径**（ADR-REFACTOR-04）。两套各写一份
   公式是这类项目最典型的分叉来源。

## 后果

- 正向：玩家能看到"理论能力 vs 实测吞吐"两条线，而不是只有一个数字；
  15% 的门也顺带校验了引擎的时间模型有没有悄悄漂移。
- 负向：解析层需要一堆假设（`availability_factor` 0.85、`tail_loss` 5%、
  `batch_mix_factor` 0.9），这些**都是 assumption 级**，不能拿去当结论；
  它们在配置里带 `level`，改了就变成"玩家的假设"，不是"项目的事实"。
- 未做：自动求解器（D10 选交互重摆）；多仓/多层联合优化。

## 拒绝过的方案

- **用解析层替代仿真出一份"更快"的 KPI**：快，但会把排队与交通瓶颈抹掉，
  而这恰恰是本项目最强的部分，也是课程 ch3.6"数字孪生"要的东西。
- **两套各写一份公式**：短期省事，长期必然出现"仪表盘说 100、仿真跑 80"却查不出
  是谁错——B1/B2 这种一倍量级的差异就是这么来的。
