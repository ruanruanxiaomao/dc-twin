# ADR-REFACTOR-07 · R3 设备类型层：车型、AST 耦合与按车型采购

- 状态：已实施（R3）
- 方案依据：`模拟运营游戏_资料驱动重构方案书_生产实际与用户自由度.md` §6.2 / §11 R3 / D5 / R12
- 相关：ADR-REFACTOR-01（货架按存取机理）、ADR-REFACTOR-02（设备类型库）、ADR-REFACTOR-05（默认关闭 + 分代重冻）

## 背景

R0 把设备类型库写成了配置，R1 给了每个 SKU 一个集装单元，R2 让货架有了存取机理。
但引擎里**始终只有一种车**：

```python
self.model = fleet["models"][0]          # 全车队共享一份参数
```

后果不是"少了个功能"，而是**三个东西同时是假的**：

1. `equipment_spec.types` 的 10 类设备没有任何代码读取，等于文档；
2. `fleet_spec.models` 是数组，但写第二个车型不会有任何效果；
3. `BUY_AGV` 只能买默认车型，"采购决策"没有可选项。

## 决策一 · 车型是车队的第一类实体，逐车携带

`Robot` 新增 `model_id`，参数（电量、速度、能耗、充电功率、最小间隔）**逐车**取自
该车型。`self.model` 保留为"默认车型"，只为兼容既有单车型路径。

`min_sep` 也从全局改为逐车：

```
min_sep = 2 * (hypot(length, width) / 2 + safety_margin)
```

一对车的安全间隔取两者较大值。单车型时它与原全局值**逐位相等**（同一公式），
所以默认产物不变；混编时大车才真正按大车的外廓留距离。

> 首版把安全间隔留在全局，混编车队里大车会按小车的间隔贴着走——不会报错，
> 只是物理上撞了。

## 决策二 · 车型必须能落到一个设备类型

`fleet_spec.models[].equipment_type` 指向 `equipment_spec.types` 的键，缺失即
`check_equipment` 判红。这条不是形式主义：设备类型是载荷、AST、可服务高度、时间模型
的唯一来源，落不到它，"设备库"就只是一张没人用的表。

映射时踩到一处真实不一致：`AMR-250`（250 kg）最初被我映射到 `amr_bin`，而后者额定
**50 kg**——因为它是"车驮料箱"的机型。现场是**车驮货架**，应映射 `agv_latent_rmfs`
（1000 kg，顶升 100 mm）。这个错会被判超载，属于"配置一写错就立刻暴露"的好错误。

## 决策三 · AST 耦合按**货架组**选择进入，且必须留痕

`aisle_width_for()` 的优先级：

1. `ast_enabled` **且**该组声明了 `equipment_type` → `宽 = AST/1000 + 净空`；
2. 组内显式 `aisle_width`；
3. 默认横通道宽。

**第一版把显式宽度放在 AST 之上，结果是空开关**：出厂布局每个货架组都写着
`aisle_width: 4.0`，于是 AST 打开了也一条巷道都不变，而所有门都是绿的。测试
`test_ast_expansion_changes_pitch_not_location_count` 抓到了它（货架行距完全没变）。

现在的语义是"声明了设备类型 = 允许该组被它驱动"，被覆盖的显式值记在
`explicit_width` 里，审阅时能一眼看到"为什么这条巷道是 2.0 不是 4.0"。

两条配套规则：

- **低于通道下限必须夹紧并留痕**（`clamped: true`）。窄于 `one_way_min` 的巷道车过不去，
  静默采用等于生成一条"仿真能走、现实撞墙"的通道。夹紧不是错误，不报告才是。
- **全局没有任何组声明 `equipment_type` 时直接报错**。单组不声明是合法的（豁免），
  全都没有则是"开关开了但不可能生效"——这种配置必须炸，而不是全绿。

## 决策四 · 采购：`BUY_EQUIPMENT` 与 `BUY_AGV` 并存，金额随事件

- `BUY_EQUIPMENT`：`{wid, model, home?}`，按指定车型买入，发 `CMD_BUY_EQUIPMENT`，
  事件里带 `capex_cny`。
- `BUY_AGV`：保留为别名（默认车型），**事件类型仍是 `CMD_BUY_AGV`**。改名会让既有
  事件流与存档里的记录静默变成另一种东西。

金额随事件走，而不是"引擎读成本表"或"经济层猜车型单价"：

- 引擎不该知道会计口径；
- 经济层也不该维护第二张价目表（那必然与 `fleet_spec` 漂移）。

采购**不进经营利润**（capex 是资本支出），但进现金与守恒式。

> 实现时踩到一个真 bug：`_post` 里 `if account == "Capex:Robot"` 才累加 `capex`。
> 新科目 `Capex:Equipment` 的钱扣了现金、却不进 capex 汇总——**现金对、报表错**。
> 改成所有 `Capex:` 前缀都计入。这类偏差靠"看现金"永远发现不了。

## 决策五 · 快照 3.1 → 4.0，且**不需要重冻**

新增的持久字段只有每台车的 `model_id`。它是真状态：丢了它，续玩会按默认车型重建
全车队，电量/速度/能耗/间隔全部退回，而"台数一台不少"。

按 D2，旧档显式拒绝，不做迁移。

**本阶段不需要 v4 重冻**：默认 `fleet_spec` 只部署 `AMR-250`，`multi_model=false`，
`sim_state` 不输出 `model` 键，AST 默认关闭，布局无货道元数据——
`step_baseline --check` 仍与 v3 逐字节一致。这由 `check_equipment` 的 `DEFAULT_OFF_OK`
持续守着，不是一次性结论。

## 未做（明确边界）

- **上架深位选择、移动式开合、穿梭车换巷时间**仍未进 tick（与 R2 同一边界）。
- **`BUILD_STATION` / `MANUAL_ASSIGN`** 仍是占位，调用即抛。
- **多车型的交通影响**只做到"按各自外廓留间隔"；换道优先级、窄巷道会车让行未差异化。
- 设备类型里的 `time_model` 仍只服务解析层（`capacity_model`），未参与 tick 服务时长——
  那会改服务时间分布，属于另一次重冻。

## 后果

- 车队从"台数"变成"车型 × 台数"，`BUY_EQUIPMENT` 才有真实决策内容（价格不同、参数不同）。
- 窄巷道第一次能真的变窄，且变窄的理由可审计（AST + 夹紧记录 + 被覆盖的显式值）。
- 快照 4.0 之后，旧存档一律拒绝——当前只有测试槽，无损失。
