# ADR-GAME-10 · 批次 / 效期 / FEFO（P6b）

- 状态：已采纳（2026-11-12）
- 上下文：P6a 让引擎有了 (SKU × 库位) 账，但**没有批次**——同一 SKU 的货混成
  一个数字，"先到期先出"无法表达，过期也无法发生。仓储课上真正要考的
  "效期管理"在 P6a 里是空的。

## 决策一 · 效期按**仿真秒**计，且必须能在 1 小时窗口里观测到

真实的保质期是天/月级。baseline 的 horizon 是 3600 s，如果按 30 天计效期，
**一个批次都不会过期**——P6b 的全部行为在验证窗口里不可观测，等于死代码。

取 A/B/C = 2h/4h/8h（`inventory_spec.expiry.shelf_life_s_by_class`），
期初批次按 `initial_lot_life_fraction` 给"还剩多少寿命"，于是 baseline 里有
124 个批次、1657 件会在期内到期。

**这是演示口径，与 `cost_spec` 的 demo 价、`tariff_multiplier=5.0` 同性质**，
必须与真实保质期区分开写。默认开关 `expiry.enabled` 关掉后，事件流与 v2 基准
**逐字节一致**（`tests/unit/test_inventory_lots.py` 钉住了这一点），
所以这套压缩不会污染"效期关闭"的旧行为。

## 决策二 · 到期报废**不进 P&L**（`waste_posting = "none"`）

这一条与 ADR-GAME-09 决策一同源：采购成本从未入账（存货是"暗资产"），
所以把报废记成费用，会凭空造出一笔从未支付的成本，现金会莫名减少。

现状：报废量 `expired_units` / `expired_value` 是 **KPI 与事件**（可审计、可断言），
不进现金/利润；HUD 单列一张卡，不并进"变动成本"（否则玩家会以为扔货和发货同价）。

要把它变成真实现金损失，必须和 COGS 一起做：新 ADR + 重标 `tariff_multiplier` + 重冻，
三件事缺一不可。

## 决策三 · 报废时刻必须进"调度事件"

`step()` 里有空闲跳 tick：不 busy、无队列、无到期事件时，tick 会直接跳到下一个
预定事件。如果把"批次到期"只当成 tick 内的扫描，跳 tick 会**直接跨过到期时刻**，
批次永远不会过期。

这和 t=0 的故障被跳过是同一类 bug（引擎里已有注释）。所以 `lot_heap` 的最小
到期时刻必须参与 `scheduled` 列表，并让 `due=True` 阻止跳 tick。
`check_expiry` 的"漏报"判据就是为这条兜底：窗口内到期的批次，必须有报废事件或被拣出。

## 决策四 · 内部移库不重算效期

仓储里的经典错：货搬到拣选面当成"新收货"，重新给一个保质期，于是临期货永远不过期。
`_inv_move_lots()` 保留原 `expiry_t`，`check_fefo` 对 `PICKFACE_REFILL` 校验
"同 lot_id 效期不变"。

## 决策五 · 数据里必须有"日期码倒挂"，否则 FEFO 是假开关

第一版数据里"后到货 = 晚到期"，于是 FIFO 与 FEFO 给出**完全相同**的结果：

```
baseline  FEFO expired=1657  |  FIFO expired=1657
holiday   FEFO expired=1652  |  FIFO expired=1652
```

这不是实现问题，是数据没有区分度。生成器因此对一半的临期库位做**日期码倒挂**
（最后到货那批的剩余寿命最短），这正是 FEFO 存在的现实理由（供应商清库存、拼车、
调拨）。改完之后：baseline 1657 vs 1660、holiday 1652 vs 1657。

## 决策六 · 不做 level_06，并把原因写进状态表

即使有了倒挂，FEFO↔FIFO 的差距只有 **3–5 件（约 0.2%）**。原因是：完成单量被车队
运力压在 ~40 单/小时，而库位有 392 个、SKU 240 个，订单很少重复打到同一个多批次库位。

把"批次策略"做成一关的胜负条件，玩家切与不切几乎同分——那是一个**假选项**，
和 P6a 时拒绝做 `BUILD_STATION` 的理由一致（扩站台已被 `check_station` 证伪）。
所以 P6b 只交付：批次账、FEFO、到期报废、以及四道门；关卡留在 level_05。

要让这个杠杆变真，得改需求模型（订单集中在少数 SKU）或大幅提高车队/时长，
那是另一个阶段的事，且会再次打破基准。

## 决策七 · 快照 3.0，旧档显式拒绝

- `SNAPSHOT_SCHEMA` 2.0 → **3.0**；`inventory.schema` 1.0 → **2.0**（加 `lots`）。
- 效期开着却没有 `inventory.lots` 的档：**直接 raise**。补一份"每库位一个批次"的假账
  能跑，但所有效期都是错的，FEFO 会静默退化成先到先出。
- 批次数量与聚合结存不一致（`sum(lots) != stock`）：raise。
- 恢复时**重放对账**要把 `STOCK_EXPIRED` 当作扣减——漏了它，第一次过期之后
  每对 (sku, loc) 都会差出报废量，看起来像"引擎多记了库存"。

## 决策八 · 基准是三代的，且 KPI 清单要跟着补

v1（step 化重构）、v2（P6a 库存）、v3（P6b 批次）并存，旧的一律不覆盖；
`REFREEZE_OK` 要求"比新基准一致 **且** 比旧基准必须不同"。

顺带修一个 P6a 的遗留缺口：`kpi_baseline.METRICS` **根本没有收录库存指标**
（缺货率、持有成本、报废量都不在清单里），所以 P6a 重冻报告显示"KPI 变 0 项"——
不是真的没变，是基准没收录，回退时没有任何门会红。现在 30 项 → 42 项，
8 场景共 336 项指标全部冻结。

## 后果

- 正向：效期成为可断言的对象（永不出过期品、报废不漏报、批次账可重放），
  且"关掉效期 = 回到 v2"这一条把改动边界钉死了。
- 负向：演示压缩后的效期（2h/4h/8h）**不是真实保质期**，不能拿去做业务结论；
  15.8% 的期初库存在 1 小时内报废，是"这批货本来就临期"的设定，不是运营水平。
- 未做：多仓调拨、批次级成本（COGS）、WMS 对接、拣选面参与拣选路径。
